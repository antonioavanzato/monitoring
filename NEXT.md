## Незакрытые задачи

### 1. Подключить ALGA

Владелица не была доступна из-за двухфакторной. Когда появится:

```bash
yc init                      # выбрать «создать новый профиль», назвать alga
```

Вход открывается в браузере по умолчанию. Если там не тот аккаунт — скопировать
адрес из адресной строки и открыть в браузере, где залогинена ALGA; ответ всё
равно вернётся в терминал. Каталог: `b1gjcf3ucce90qgigaii`.

Затем **полный** запуск, без `--code-only` — нужно выпустить ключ для третьего
облака:

```bash
cd ~/monitoring/backend && ./setup.sh
```

Пароль спросит заново, можно задать тот же.

### 2. Отозвать засвеченный токен

OAuth-токен аккаунта ALGA попал в переписку. Для входа в облако он уже
бесполезен (Яндекс отключил обмен таких токенов на IAM), но доступ к другим

### 3. Холодные старты — выяснено 28.07

**Причина:** `hub-api` вызывается только пингом раз в три минуты, другого
трафика нет вовсе. Экземпляр столько не живёт, поэтому каждый вызов холодный.
85% — не поломка, а следствие.

Как установлено, по шагам:

- пауза между вызовами 150–220 сек, все вызовы холодные без исключений →
  экземпляр живёт меньше 150 секунд (измерено по логам);
- `functions_inflight` = 1 всегда → параллельности нет, версия про
  одновременные запросы опровергнута;
- сырые точки: 7 групп по 3 отсчёта за 20 минут → ровно 7 вызовов, то есть
  весь «трафик» это пинг.

**Пинг раз в три минуты не работает.** Он не удерживает ни одного экземпляра
тёплым — это измерено, а не предположено. Тратит ~14 000 вызовов в месяц зря.

Что можно сделать (решения пока нет):
- убрать пинг совсем — первый запрос пользователя и так холодный;
- участить до раза в минуту, но сперва замерить, доживает ли экземпляр 60 сек;
- облегчить инициализацию: 400–500 мс уходят на тяжёлые `require` верхнего
  уровня, ленивая загрузка внутри обработчика их срежет.

Замерить настоящий TTL можно на нашей `cm-admin-api`, не трогая CreatorHUB:
дёргать с паузами 30/60/90/120 сек и смотреть, с какой начинаются холодные старты.

### 4. Расхождение с биллингом — закрыто 28.07

Причина найдена: `functions_finished` это счётчик за **скользящую минуту**,
который Monitoring отдаёт каждые 15 секунд. Один вызов виден в 3–4 подряд
идущих точках, и сумма точек завышала итог втрое.

Исправлено: агрегатор измеряет поправочный коэффициент на свежем часе
(сумма точек ÷ число серий) и делит на него длинные периоды. Не измерилось —
поправка не применяется, поведение остаётся прежним.

После правки Avanzato показывает ~15 400 вместо ~54 000, что укладывается в
диапазон 15 000–25 000, скрытый за биллинговым `0.02 1m*invocation`.

Доля холодных стартов от поправки не зависит: она отношение двух метрик с
одинаковым завышением.

### 5. Находки по коду hub-api (28.07, изучен исходник)

**Таймер убирать нельзя.** Мой ранний совет был неверным: обработчик пинга
делает не только `warmup()`, но и `orders.resendPending()` — дослыает в
Telegram заявки, у которых пуш не прошёл за последние два часа. Прогрев в
нём не работает, дослатель работает. Это два разных дела в одном месте.
Стоит поправить комментарий в коде, чтобы через полгода не считать, что
keep-warm действует.

**Ограничитель частоты фактически отключён.** В `index.js`:

```js
const rl = new Map();   // in-memory на инстанс функции
```

Замерено: 85–100% вызовов приходят на новый экземпляр, значит `rl` каждый раз
пустой и порог «20 за 10 минут» не срабатывает никогда. `POST /orders` —
публичный роут без авторизации, его можно долбить неограниченно. То же
касается защиты от перебора пароля на `/auth/login`.

Это важнее самих холодных стартов. Варианты: ограничение на уровне API
Gateway, счётчик в YDB, либо сознательно принять отсутствие защиты — но
знать об этом, а не полагаться на мнимую.

**Инициализация 400–500 мс** — это в основном загрузка `ydb-sdk` вместе с
`@grpc/grpc-js` в `db.js`. Ленивая загрузка обработчиков (`students`,
`events`, `orders`) по образцу уже применённого
`require('./handlers/config')` внутри хендлера даст выигрыш, но небольшой:
`db` нужен почти всем маршрутам.

**Трафик hub-api:** 482 вызова в сутки, из них 463 — таймер, и лишь ~19
настоящих клиентских обращений. Холодный старт стоит этим 19 лишние
полсекунды. Правку кода ради этого я бы не делал.

### 6. Вторая полоска «время выполнения» (решили отложить)

Точно посчитать ГБ×часы не выходит: нужна выделенная память каждой функции, а
сервисный аккаунт имеет только `monitoring.viewer`. Оценка по
`functions_sum_memory` даёт 2,5 из 10 для Avanzato — завышает относительно
биллинга, то есть безопасно. При нынешнем запасе смысла мало; вернуться, если
расход начнёт расти.

## Полезные команды

```bash
cd ~/monitoring/backend

./setup.sh --dry-run     # репетиция: показывает все команды, ничего не меняет
./setup.sh --code-only   # перелить только код функций, пароль и ключи не трогая
./setup.sh               # полный запуск: ключи, секреты, деплой
./verify.sh              # сверка цифр дашборда с сырыми данными Monitoring
./metrics-names.sh       # какие метрики вообще есть в каталогах
./coldstart.sh           # доля холодных стартов по функциям, ритм вызовов
./coldstart-logs.sh hub-api 20m   # по каждому вызову: холодный или тёплый
./raw-series.sh functions_finished 20   # сырые точки метрики и способы подсчёта
```

После правок фронтенда достаточно `git push` — GitHub Pages пересоберётся сам.
На телефоне обновлять через ⌘⇧R: service worker держит кэш, его версия в `sw.js`.
